# DEETOO — Documentation Alignment Audit

## 1. Executive Summary

**SIGNIFICANTLY MISALIGNED.** The repository contains substantial application and domain scaffolding, useful ownership guards, state machines and local tests. Its core transaction still violates the documented payment gate, durable persistence, custody, provider verification and financial disbursement rules. It is not ready to be treated as a trustworthy production marketplace.

The strongest blockers are: unpaid orders reaching merchants; production-capable simulation/fallback paths; inconsistent migration/runtime schemas; nontransactional event and financial effects; weak delivery proof and ongoing location disclosure after delivery; unrestricted refund roles; and settlement calculation that does not filter by merchant.

All 18 supplied PDFs were reviewed, including the consolidated specification. The repository was inspected directly across all 26 requested domains; profitability was assessed separately as a 27th reporting category. Prior sprint/completion reports were not used as implementation proof. Document instructions were treated as audit criteria, not authorization to change code.

The matrix contains **288 assessment rows**, with **165 explicit requirement IDs** traced in a document-namespaced index. Counts: 7 IMPLEMENTED, 193 PARTIAL, 25 MISSING, 61 CONTRADICTS_DOCUMENTATION and 2 NOT_APPLICABLE. Rows include requirement, schema, RBAC, API and state-transition assessments; some refer to the same underlying defect. These counts are **not a product completion percentage**. Repeated baseline statements are consolidated; illustrative examples, document metadata and expressly deferred features are not missing MVP implementations.

**Evidence limits:** This is a static documentation/source audit, including inspection of test bodies. No test suites, migrations, real provider transactions, deployment checks, device UAT or restore drills were run. A test file proves coverage exists, not that the documented guarantee passes in PostgreSQL or production. External business/legal approvals and pilot results were not supplied; their absence from this repository is recorded as missing evidence, not proof they never happened.

**Read-only verification:** 190 pre-existing files were hashed before and after inspection; none changed. Only audit report artifacts were added. [Verification record](/home/jenny/Documents/ChatGPT/Deetoo/docs/documentation-alignment-audit/read-only-verification.json).

### Authoritative documents disagree in several places

1. **Prepayment Order creation:** individual PRD §6.1, State Machines §5 and Payments/Ledger §6 describe payment-confirmed creation/confirmation. The master §5.1/§8.8/§9.2 explicitly permits a `PENDING_PAYMENT` Order first. Creating a pending row is therefore not inherently a defect. Creating merchant-visible `PLACED` before capture contradicts both versions (A43).
2. **State names and terminal behavior:** the individual Payment model uses CREATED/PENDING/EXPIRED while the master uses INITIATED/PENDING_CUSTOMER; the individual Order model omits PENDING_PAYMENT. Delivery cancellation/failure rows also differ around pickup. Resolve a canonical model explicitly. Both preserve a distinct payment lifecycle, meaningful custody evidence and controlled post-pickup handling; the runtime shortcuts are not justified by these differences.
3. **API and schema contracts:** the individual API uses `/v1` and customer/branch-oriented paths; the master uses `/api/v1` and different command shapes. Individual and master schema names/ownership details also differ. Path or table renaming alone is not proof of a missing capability, but undocumented incompatibility needs an explicit contract decision.
4. **Ops refunds:** the individual RBAC matrix limits Ops to reads; the master permits an emergency/policy exception. Neither supports unrestricted refunds without thresholds, policy and audit. Do not broaden permissions to reconcile tests.
5. **Ledger timing is not a contradiction:** Payments/Ledger §8.1 and master §9.6 explicitly show capture-time revenue/merchant-payable posting and delivery-time Rider earning. A narrative journey listing Ledger after Delivery does not prohibit capture-time posting. Actual amounts, durable posting, holds and settlement eligibility remain defective.

1. Default privileged credentials/secrets, backend role/policy gaps, completed-order GPS exposure and leaked/self-satisfiable proof.

## 8. Revised Alignment Waves

**Minimum recommendation: four dependent repair waves.** These are repair boundaries based on this audit, not acceptance of previous wave-completion claims. Resolve the document conflicts as a prerequisite within the first wave; a separate redesign/audit wave is unnecessary.

1. **Durable and authorized foundation.** Freeze canonical states/API/schema decisions; make migrations and runtime storage agree; remove production seed/default-secret/fallback paths; enforce remaining RBAC, active-lifecycle privacy and fail-closed readiness; implement the transactional outbox/worker foundation and correct CI. Exit: real PostgreSQL migration and failure tests, complete documented authorization matrix and durable event replay.
2. **Correct paid-order and ledger transaction.** Bind quote to immutable cart/configuration, enforce idempotency/hash conflicts, implement real provider verification and pending→paid merchant gate, coordinate cancellation/refunds, implement approval/reservation and correct ledger allocation/recovery. Exit: real sandbox capture/refund and DB concurrency/crash tests prove exactly one correct economic effect.
3. **Reliable fulfilment and realtime delivery.** Enforce scheduled dispatch eligibility, atomic offer acceptance, custody/proof, completion recovery and true notification/reconnect behavior. Exit: paid order progresses through merchant, Rider and delivery with negative custody/proof tests, restart recovery and four-app/device evidence.
4. **Verified disbursement and launch operations.** Build merchant/Rider batch selection from uniquely reserved eligible payable entries, holds and verified transfers; reconcile provider/bank statements; complete required privacy/operations/analytics gaps and actual load/restore/pilot evidence. Exit: no duplicate/cross-merchant disbursement, accurate statements/economics and documented launch-gate approval.

Combining waves is possible organizationally, but does not remove these dependency gates. No repairs were started.
