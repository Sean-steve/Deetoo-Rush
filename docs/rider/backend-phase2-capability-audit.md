# Rider backend capability audit — Phase 2

**Scope:** read-only source and API-contract audit of all **24 approved Rider Android frontend screens**, against existing DeeToo backend services, database migrations, shared validation schemas, and the legacy connected Rider Android client.

- **Date:** 11 October 2026
- **Baseline:** `6bef5075b460c1a2f601f56332d5edcd15885a1c`, `feat/rider-android-consolidated-24`.
- **Code changed during audit:** None in API, database, UI or tests. Only audit documentation is committed.
- **Outcome:** **5 Existing core / 16 Partial / 3 Missing core**; **0/24 integrated** with the approved frontend. This is an audit, not a deployment/runtime or Android visual certification.
- **Machine-readable matrix:** [backend-phase2-capability-matrix.json](./backend-phase2-capability-matrix.json).

## Rules for interpreting the matrix

**Existing** = a Rider-accessible (or appropriately participant-accessible) server workflow exists for the core screen, **not** that every approved UI control is backend-ready. **Partial** = reusable domain/API exists but functional gaps remain. **Missing** = core Rider-scoped capability absent despite possible admin/internal primitives. All 24 approved screens currently run in the explicit development-only mock frontend; the original connected `RiderNativeApp` is separate until integration. **Priority P0** = security/identity/safety/financial control or blocking launch prerequisite; **P1** = product workflow or data contract; **P2** = non-blocking presentation/enrichment. P0 is not a promise to implement before reviewing architectural choices.

API paths below are relative to **`/api/v1`** (mounted in [app.ts](https://github.com/Sean-steve/Deetoo-Rush/blob/6bef5075b460c1a2f601f56332d5edcd15885a1c/apps/api/src/app.ts#L27-L30)). Existing route names are not automatically authorization to use them in Rider; Admin/Finance scopes remain protected.

## Confirmed gaps: architecture and implementation decisions for Phase 3

### P0 — guardrails and missing trust boundaries

**G01 · Rider registration / onboarding profile completeness (screens 2–5).** Current `/auth/register/customer` is customer-only. Admin provision via `/admin/governance/provision` creates a **PENDING** RIDER identity and DRAFT rider profile; `/rider/status` initializes an authenticated Rider profile when missing. Decide explicit self-service Rider signup policy vs invitation-only onboarding. Implement verified identity/contact/address/emergency profile, document/equipment evidence+expiry, review/rejection/resubmission timeline and binding to approval. Do **not** mark a rider eligible from document-upload existence alone. [Governance service](https://github.com/Sean-steve/Deetoo-Rush/blob/6bef5075b460c1a2f601f56332d5edcd15885a1c/apps/api/src/modules/admin/governance.service.ts#L75-L145) · [Rider creation](https://github.com/Sean-steve/Deetoo-Rush/blob/6bef5075b460c1a2f601f56332d5edcd15885a1c/apps/api/src/modules/rider/rider.service.ts#L66-L106) · [Current submit validation](https://github.com/Sean-steve/Deetoo-Rush/blob/6bef5075b460c1a2f601f56332d5edcd15885a1c/apps/api/src/modules/rider/rider.service.ts#L204-L246).

**G02 · Verified identity and vehicle update security (screens 4, 24).** `RiderProfileUpdateSchema` allows vehicle type/plate; `RiderVehicleSchema` accepts client-selected `ACTIVE`. `riderService.updateProfile/updateVehicle` applies changes directly without mandatory reverification of already-approved riders. Introduce a pending-change/approval model, versioned verification and audit, never allow self-activation based on client input. [Validation](https://github.com/Sean-steve/Deetoo-Rush/blob/6bef5075b460c1a2f601f56332d5edcd15885a1c/packages/validation/src/index.ts#L584-L596) · [Update](https://github.com/Sean-steve/Deetoo-Rush/blob/6bef5075b460c1a2f601f56332d5edcd15885a1c/apps/api/src/modules/rider/rider.service.ts#L153-L200) · [Vehicle update](https://github.com/Sean-steve/Deetoo-Rush/blob/6bef5075b460c1a2f601f56332d5edcd15885a1c/apps/api/src/modules/rider/rider.service.ts#L250-L281).

**G03 · Rider-initiated payout request and destination (screens 18, 24).** Payout calculation/approval/pay is restricted to Admin/Finance; masked/encrypted provider payout destinations are managed by Admin/Finance. The approved withdrawal screen must not call these protected routes or mark a payout PAID. Decide whether DeeToo permits Rider-initiated **requests** (queued for finance validation) or scheduled payouts only. If enabled, introduce Rider-scoped `GET/POST /rider/payout-destinations`, `POST /rider/payout-requests`, own-history and confirmation/OTP with limits, holds, duplicate prevention, and provider-evidence-only settlement. Preserve maker/checker and reconciliation. ## Proposed Phase 3 delivery order

1. **Contract/security hardening first:** correct support cross-party linking and administrator-only final resolution (G13); decide Rider self-signup policy; add durable verification/equipment and pending change/review; write cross-role and forged-document tests.
2. **Rider history and incident intake:** design scoped read models and incident reporting with evidence and administrator-only resolution. These unblock three missing primary screens.
3. **Finances:** decide withdrawal request vs scheduled payout; add Rider request/destination flows only if business-approved, with financial idempotency, provider callbacks, and maker/checker.
4. **Multi-order feature gate:** implement *only if approved*, after dispatch/custody/capacity tests; otherwise keep the approved screen and render a genuine unsupported/empty state.
5. **UI-supporting read endpoints:** earnings trends, performance comments, notification preferences, map/ETA adapter, completion receipt, optional account controls.
6. **Cross-app contract tests:** Customer paid order → Merchant READY → Rider assigned → pickup code → verified handover → earnings/cash obligations → payout review; include wrong-rider, stale GPS, expired offer, double pickup, invalid OTP, forged media, cash reconciliation, support party scope and incident ACL.
