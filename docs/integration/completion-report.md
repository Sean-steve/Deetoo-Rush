# Deetoo Stitch integration report

The four supplied Stitch screens are now integrated into the existing React application, with shared styling and new frontend connections to the existing domain APIs. This is not a certification that every requested production workflow is complete: the source limitations and unverified paths below remain material.

## Design system

Shared tokens define the warm canvas, burnt-orange primary, green secondary, semantic status colors, spacing, radii, shadows, motion, focus states and responsive breakpoints. Epilogue headings and Manrope body use Google Fonts with local fallbacks. The supplied SVG logo replaces the bicycle mark. Lucide remains the icon system. Layouts use mobile-first 640px and 1024px boundaries, a 1240px content width and 44px primary touch targets.

Shared components include buttons, fields, inputs/selects/textareas, cards, badges, skeletons, empty/error states, native focus-managed dialogs, navigation, operational sidebar/layout, price breakdowns, status badges, timelines, metrics, support conversations, notifications and a coordinate overview. Domain transitions remain API actions; presentation does not implement a replacement state machine.

## Customer

- Discovery, search, cuisine/open filters, sorting, serviceability, location, addresses, restaurant/menu browsing and modifiers retain existing data flows under the new shared visual system. Sample ratings/promotions are not fabricated.
- Authentication, registration/recovery, profile, address editing and security/session views remain in the existing application.
- Cart now adds through the existing cart endpoint and supports quantities, removals and promotion actions. Modifier controls support keyboard activation.
- Checkout uses the server quote, expiry, address snapshot, authoritative minor-unit prices and idempotent order creation.
- Order history/detail, timeline, M-PESA initiation, payment/refund status, cancellation and authorized tracking are connected to existing endpoints.
- Support cases, conversations and notifications are connected to account APIs.
- Card entry/tokenization is not implemented: the supplied card provider is a development adapter, with no existing secure hosted card UI. No fake payment token or successful payment is generated by the UI.

## Merchant

- Kitchen display uses real branch-scoped orders in incoming, cooking/prep and ready columns. Accept/prep minutes, reject, preparing, ready, rider assignment/arrival and handover code use the existing APIs.
- Branch selection/status now uses real accessible branches instead of hard-coded options/local status changes.
- Existing menu/category/item/modifier CRUD and availability remain in CatalogueManager, using shared primitives and branding.
- Business profile, team roles/branch access, invitations, branch settings and opening intervals have API-backed forms using existing schemas.
- Finance/settlements, account support and security/session views are connected.
- Browser verification covered login, branch loading, kitchen empty state, business profile, team data, arrival of the customer-created order, acceptance with prep time and transitions to preparation and ready, plus unassigned rider/handover-code display. Not every catalogue mutation, invitation, role edit or settlement action was submitted in the browser.

## Rider

- Offers use server expiration and accept/reject actions. Delivery milestones, navigation links, pickup verification, OTP completion, release/failure reporting use existing APIs and shared validation schemas.
- Earnings/payouts and support read existing APIs. Sample offer earnings were deliberately omitted.

- Alternative photo/signature proof capture is not implemented; existing backend proof support is unchanged.

- Existing users, rider approval/suspension, audit and health views remain.
- Added API-backed orders, dispatch/assignment/retry/release, merchants/approvals, branches, zones, payments/refunds/reconciliation, ledger/accounts, settlement and payout calculation/approval/payment, incidents, support, notifications, jobs, risk and dispatch configuration/kill-switch views.

## Remaining differences and limitations

1. **Backend rider role enforcement:** `/rider/offers/active` returns 200 to an authenticated customer. The router requires authentication but does not require the rider role. A failing regression test preserves evidence. Frontend route guards are not a security substitute. This existing backend issue was not changed under the explicit backend-preservation constraint.
2. **Realtime:** existing SSE/event broker/routes are preserved byte-for-byte. Their channel endpoints do not authenticate subscriptions, and the source frontend had no subscription to preserve. New views refresh authenticated APIs every 3–5 seconds and on online/visibility events. This is an intentional deviation from instant SSE integration; private channel authorization must be solved in the backend before safely wiring it.
3. **Maps:** there was no existing frontend road-map renderer. The new admin coordinate overview plots actual available coordinates and explicitly identifies itself as an overview, not a road map. Rider navigation uses existing backend links. Customer tracking displays authorized server updates. No simulated roads, routes or rider locations were introduced.
4. **Payments and infrastructure:** development provider behavior and repository fallbacks are preserved. No live money movement, provider callback certification, Postgres/PostGIS deployment or production Redis verification was performed. Backend-supplied placeholder proxy numbers and fixed sample offer earnings are not presented as real contact/earnings data.
5. **Visual scope:** the ZIP contains four full screens plus a logo and sample portrait, not a complete screen-by-screen design for every requested workflow. Additional views apply shared Stitch styling. Sample portrait, promotions, fabricated reviews, ETAs, operational figures and inappropriate cross-role navigation were excluded.
6. **Verification coverage:** physical delivery, provider callbacks, every CRUD/action/error/offline scenario, photo/signature proof and all responsive combinations are not fully verified. The task's strongest “every workflow complete” criterion is therefore **not satisfied** by this handoff.
