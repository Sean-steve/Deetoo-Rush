## Executive verdict

**FAIL — visual equivalence; PASS — single active Customer route; backend functionality must be retained.** PR #39 corrected routing: `apps/customer-web/src/main.tsx` serves `ConnectedCustomerShopping` at `/customer/*`, and the new eight-screen Merchant experience remains untouched. But the connected implementation was written as **separate JSX/view structures** rather than adapting the approved `App`, `ShoppingPreview`, `OrdersPreview`, `AccountPreview` and `SupportPreview` components. Consequently many approved HTML elements, cards, art, interaction controls, classes and layouts are never rendered, even though the approved CSS is in the bundle. **Do not try to resolve these gaps with CSS overrides alone.**

### Verified shared styling, font and entrypoint differences

1. **Identical approved stylesheets:** the following blobs have the same SHA on approved branch and main:
   - `src/styles.css` — `7c3bb03d21f7500a03db00e752f93da447a3f974`
   - `src/shopping.css` — `02feef426530f0decd15f2fc5b97fd048e898c4e`
   - `src/orders.css` — `55e2b407d9c2655b8e49f5801c16c04aa4eb49d4`
   - `src/account.css` — `a0ce8c33b37fd4f4a0a5531fc2b483bf6e315c8f`
   - `src/support.css` — `bde9da7c9d03bf826696dc6375a3c4cfe9b18217`
   - `packages/customer-ui/src/index.tsx` — `0f070b1ecf9bb01337edd9053e3f68055f75b7de`.
2. **Typography mismatch — confirmed:** `apps/customer-web-next/index.html` loads `DM Sans` (400–800) and `Manrope` (400–800). The canonical `apps/customer-web/index.html` loads `Epilogue` (600–800) and `Manrope` (400/600/700), **not DM Sans**. Approved `styles.css` sets `:root { font-family: "DM Sans", "Manrope", ... }`. Canonical `apps/customer-web/src/main.tsx` also imports `src/index.css` (Tailwind + global `body`, `h1/h2/h3` theme rules) and calls `installTheme`; the independent design-first entry imports only the five dedicated CSS files. **Measure actual computed font stacks, weights, sizes, colors and cascade order** before altering either global theme. The missing DM Sans font and differing global rules are verified *possible causes* of rendered disparity; specific pixel impact requires screenshots/computed styles.
3. **Design tokens remain available:** `--dt-green:#009d5e`, `--dt-green-dark:#007c49`, `--dt-mint:#e8faef`, `--dt-dark:#111a30`, `--dt-muted:#596d87`, `--dt-border:#e2eae7`, `--dt-radius:16px`. The original shell targets 74px header / 242px sidebar and desktop layout; validate computed values in the canonical build. Global `--deetoo-*` tokens are a separate theme, **not replacements for the approved `--dt-*` tokens**.
4. **Unchanged visual primitives are not enough:** both builds use `Header`, `Sidebar`, `Button`, `Panel`, `Badge` from `App.tsx`/`packages/customer-ui`, but backend-connected screen bodies independently render `LiveDiscovery`, `LiveShopping`, `LiveOrders`, `LiveAccount`, `LiveSupport` with new `dt-live-*` CSS. The extra connected CSS files have their own colors, widths, spacing and typography; verify cascade as well as absent DOM structures.
5. **One active route; preview is NOT the live app:** `pnpm dev:customer` serves `/customer/*` from `apps/customer-web`; `pnpm dev:customer-next` provides the approved visual fixture by default. Comparison must use the same fixture state and viewport, with clear `fixture` vs `live` labelling.

### Backend contracts to preserve during Phase 2 (minimum regression scope)

**Discovery & shopping:** public restaurants/categories/branch-menu, location/serviceability, item modifier bounds, authenticated single-branch cart, promo validation, server quote with expiry, idempotent order creation, M-PESA initiation and verified capture.  
**Orders:** customer-scoped history/detail, delivery status/timeline, no invented location or ETA, completed receipt, rating authorization, cancellations/refunds policies.  
**Account:** real profile/addresses/default, verified authentication sessions and session revocation, notification list/read; channel consent/MFA/card vault/Plus/favorites **must not be fabricated**.  
**Support:** authenticated cases, messages, authorized attachment URLs, customer resolution acceptance/dispute, no false closure or uploaded-evidence claims.

Use `docs/customer-web-next-backend-integration-matrix.md` and `docs/customer-web-next-phase5-release-runbook.md` for the existing endpoint/release gates. **No component may be removed solely because its backend is missing.**

5. **Screens 14–15:** restore original support hero/chat/sidebars/progress/evidence visual system; connect real cases and messages, restricted evidence and resolution/confirmation.
6. **Remove or archive redundant active-source branches only in a separate reviewed step** after the owner's `review/customer-local-improvements` branch is audited. Do not delete the preview source, API adapters or legacy Customer code during this phase.
